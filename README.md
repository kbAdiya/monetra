# Monetra

Локальный рабочий прототип управления операциями и повторяющимися платежами. React + Vite, Node.js HTTP API, SQLite. Банковские подключения и реальные списания не используются.

## Запуск

Нужен Node.js **24.15 или новее**.

```powershell
npm install
npm run dev
```

Приложение: http://127.0.0.1:5173. API: http://127.0.0.1:4000/api/health. Одна команда запускает обе части. Если порт занят, сначала остановите предыдущий экземпляр проекта.

```powershell
npm test
npm run build
npm start
```

Последние две команды создают сборку и запускают её вместе с API на http://127.0.0.1:4000. Для отдельной разработки есть `npm run dev:server` и `npm run dev:client`.

## Как проверить прототип

1. Нажмите «Загрузить примеры» на главной странице. Добавятся 15 синтетических операций: три ежемесячных сервиса, разовые покупки и неоднозначный случай с изменившейся суммой. Повторная загрузка не создаёт копий существующих примеров.
2. В «Возможных подписках» проверьте историю, подтвердите, отклоните или исправьте предложение. Предложение само по себе не попадает в прогноз или напоминания.
3. В разделе «Повторяющиеся» откройте подтверждённый платёж. Можно исправить продавца, сумму и следующую дату, отключить напоминания или убрать расписание.
4. Для проверки напоминания задайте ожидаемую дату на сегодня или ближайшие два дня. В настройках можно изменить окно от 0 до 30 дней.
5. Добавьте операцию, обновите страницу: она останется в базе. Поиск, категории, удаление, аналитика и имя профиля работают с сохранёнными данными.
6. Если в этом браузере есть история старой версии, в настройках появится «Перенести операции». Перенос проверяет весь набор перед записью; старый localStorage сохраняется. Повторный перенос идентичных записей не создаёт копий. Если старая история содержит некорректные или будущие даты, сервер покажет ошибку и не импортирует набор частично.

## Правило обнаружения повторов

Последнее уточнение пользователя задаёт порог **три месяца**. Оно имеет приоритет над ранним вариантом Assignment 4 с двумя платежами.

- Учитываются расходы одному продавцу с одинаковой суммой до тиына. Регистр, внешние и повторные пробелы, совместимые Unicode-символы имени нормализуются. Разные продавцы с одинаковой суммой не объединяются.
- Нужна цепочка минимум из трёх последовательных календарных месяцев, заканчивающаяся последним платежом. В каждом месяце учитывается одна дата, поэтому дубликаты не увеличивают число месяцев. Частые покупки в течение месяца не принимаются за ежемесячный платёж.
- Допуск — три дня относительно общего дня списания. Для коротких месяцев день ограничивается последним числом: 31 января → 28 февраля → 31 марта → 30 апреля. Годы учитываются отдельно.
- Предложение содержит исходные платежи и остаётся неподтверждённым до решения пользователя. Отклонение сохраняется для этого сочетания продавца и суммы.
- Категория «Подписки» не является доказательством повторения. В ручной форме при выборе категории/шаблона включается видимый флажок «Повторять каждый месяц», который можно снять. Сохранение с включённым флажком — явное подтверждение расписания.

## Даты, прогноз и хранение

Операции описывают уже совершённые платежи: будущие даты запрещены. Для будущих обязательств редактируется ожидаемая дата расписания. Бизнес-дата рассчитывается в `Asia/Qyzylorda`, календарные интервалы — без зависимости от переходов времени.

Подтверждённое расписание существует отдельно от операций, поэтому история из трёх платежей не создаёт три одинаковых будущих списания. В прогноз входит одно ближайшее ожидаемое списание каждого подтверждённого расписания с датой от сегодня до сегодня + 30 дней включительно. Прошедшая дата показывается как ожидавшаяся: приложение не придумывает факт оплаты и не переносит её молча. Новый соответствующий фактический платёж с датой не раньше ожидаемой продвигает расписание на месяц с сохранением исходного дня списания.

Удаление операции пересчитывает неподтверждённые предложения. Подтверждённое пользователем расписание остаётся, пока его не уберут отдельно. Удаление расписания сохраняет историю; отменять саму услугу нужно у её поставщика.

База создаётся в `data/monetra.sqlite`; каталог исключён из Git. `MONETRA_DB` позволяет выбрать другой файл, `API_PORT` — порт отдельного API/собранного приложения. Dev-прокси использует порт 4000. Суммы хранятся целыми тиынами; связанные изменения записываются в SQLite-транзакциях.

Идентификация локального пользователя — случайная HttpOnly/SameSite cookie. Другой браузер имеет отдельную историю; очистка cookie теряет доступ к прежнему локальному профилю. Это прототип без регистрации, восстановления доступа и синхронизации устройств. Напоминания доступны внутри открытого приложения; фоновых push/email уведомлений нет. API по умолчанию слушает только 127.0.0.1.

## Проверки и ограничения

`npm test` запускает проверки правила, календарных границ, API, изоляции локальных профилей, SQLite после перезапуска и полный сценарий React-компонентов через DOM с настоящим тестовым API. Тесты создают собственные базы и не изменяют рабочую историю. DOM-тест не заменяет визуальную проверку в браузере.

Исходный Vite 5.4.11 и его дерево зависимостей имеют замечания `npm audit`; обновление сборочных зависимостей не выполнено. Не публикуйте dev-сервер в сеть. До публичного размещения нужны обновление зависимостей, отдельная проверка безопасности, полноценная авторизация и резервное копирование.

Справочная документация: [Node.js SQLite](https://nodejs.org/docs/latest-v24.x/api/sqlite.html), [Vite server proxy](https://vite.dev/config/server-options.html#server-proxy).
